# Инструкция по установке для ИИ

[English](AI-INSTALL.md) · **Русский**

Пошаговая процедура для ИИ-агента, которого попросили установить эти моды в
DeepSeek Harness. Выполняй по порядку: у каждого шага есть проверка, а в конце —
таблица разбора проблем.

> Это про **установку** готовых модов. Чтобы **создать** мод, используй
> [AI-PROMPT.ru.md](AI-PROMPT.ru.md).

## Жёсткие правила

1. **Не трогай установку DSH.** Это npm/npx-пакет, в котором лежит
   `@deepseek-ai/dsh`. Моды живут в домашнем каталоге харнесса, не там.
2. **Не перезапускай процесс `dsh web` без разрешения.** Если ты работаешь
   внутри него, перезапуск оборвёт твою же сессию. Вместо этого дай
   пользователю точную команду.
3. **Запустить свой `dsh web` можно, чужой перезапускать нельзя.** Для проверки
   установки подними второй сервер на свободном порту со своим `DSH_HOME` — это
   никак не задевает пользователя, и именно так проверялось всё, что описано
   ниже. Точная команда — в шаге 4.
4. **Не коммить и не печатай секреты.** В `$DSH_HOME/.credentials.yaml` лежат
   ключи API и секрет подписи браузерной сессии.
5. **Проверяй, а не предполагай.** Каждое утверждение ниже проверяется
   командой.

## Шаг 1 — определить окружение

```powershell
node --version        # должен быть; DSH работает на Node
$env:DSH_HOME         # пусто — значит используется путь по умолчанию
```

```bash
node --version        # то же самое в bash
echo "$DSH_HOME"
```

Домашний каталог харнесса — `$DSH_HOME`, а если переменная не задана, то `~/.dsh`
(`%USERPROFILE%\.dsh` в Windows). `web` — это браузерный интерфейс и цель по
умолчанию.

**Отсутствие домашнего каталога — не преграда.** Не дёргай пользователя с
просьбой «сначала запусти `dsh web`»: `tools/install.mjs` сам создаёт нужные
каталоги, а первый запуск `dsh web` после этого достраивает остальной профиль
вокруг них и **не трогает патч-файл** — он остаётся байт-в-байт тем же. Это
измерено на пустом каталоге, а не предположено.

**Проверка:** после шага 2 `$DSH_HOME/profiles/web/cordis.patch.yml` существует и
содержит по одной строке `- insert:` на пакет.

Если сама команда `dsh` не запускается — иди сразу в таблицу разбора проблем: в
Windows причина обычно в заблокированном PowerShell-скрипте, и там написано, как
запустить тот же бинарник через `node`.

## Шаг 2 — установить

Из корня репозитория:

```bash
node tools/install.mjs --lang ru    # либо --lang en, либо без флага
```

Если целевой профиль не `web`, добавь `--profile <имя>`. Прочитай вывод: там
перечислены найденные пакеты, пути установки и добавленные строки. Повторный
запуск обязан напечатать «все строки уже на месте» — это и есть проверка
идемпотентности.

**Проверка:** в `$DSH_HOME/profiles/node_modules/@local/` появились
`system-prompt-mod/` и `locale-ru/`, а в
`$DSH_HOME/profiles/<профиль>/cordis.patch.yml` — по одному блоку `- insert:`
на пакет.

Если сначала нужен предпросмотр — `--dry-run` покажет план без записи.

## Шаг 3 — чтобы работающая GUI это подхватила

Если сервер ещё **не** запущен — а в каталоге, который ни разу не загружался, его
нет — обновлять нечего: подними его, как показано в шаге 4, и он отдаст оба мода
уже при первой загрузке страницы.

Если сервер работает: **host-половина** новой строки загружается на лету при
изменении патч-файла, а **браузерная половина** попадает в ростер при загрузке
страницы, поэтому:

- **Обновить страницу (F5)** — достаточно, если DSH уже запущен и строка новая.
- **Перезапустить `dsh web`** — нужно, если менялись *файлы* пакета под уже
  загруженной строкой: загрузчик импортирует модуль один раз на процесс и
  кэширует его по URL, поэтому правка `lib/index.js` на диске не влияет на
  работающий сервер. Попроси об этом пользователя; сам процесс не убивай.

## Шаг 4 — проверить

`boot-check` нужен работающий сервер. Если у пользователя он уже есть — бери его
адрес. Если нет — подними **свой**: второй сервер, на свободном порту, в своём
домашнем каталоге. Чужой сервер и чужой каталог при этом не затрагиваются:

```powershell
# 1. найти запускатор; обёртку `dsh` может блокировать политика выполнения
$launcher = (Get-ChildItem "$env:LOCALAPPDATA\npm-cache\_npx" -Recurse -Filter bin.js |
  Where-Object FullName -like '*@deepseek-ai\dsh*' | Select-Object -First 1).FullName

# 2. отдельный домашний каталог, чтобы не тронуть пользовательский
$env:DSH_HOME = "$env:TEMP\dsh-mod-check"

# 3. запуск на свободном порту; --no-open не открывает браузер
node $launcher web --no-open --port 3088
```

Первый запуск создаёт всё, чего в каталоге не хватает: файлы профиля,
`storages/`, `.credentials.yaml` — а `cordis.patch.yml` не трогает. Запускай его
в фоне или во втором окне: он работает, пока ты его не остановишь.

Дальше:

```bash
node tools/boot-check.mjs                       # по умолчанию http://127.0.0.1:3080
node tools/boot-check.mjs http://127.0.0.1:3088 # только что поднятый сервер
```

Ожидаемый вывод:

```
GET / -> 200 (… bytes)
boot rows referencing /client.js: …
  OK   dsh-system-prompt-mod
  OK   dsh-locale-ru
```

Пробник читает секрет браузерной сессии из локального домашнего каталога,
выпускает ту же cookie, которой пользуется GUI, и сообщает, какие клиентские
записи попали в отдаваемый boot-граф. Секрет не печатается. Код возврата
ненулевой, если какой-то записи нет.

**Чего `boot-check` не доказывает.** Он ищет в отданной странице два имени
пакетов. Он не доказывает, что host-роут мода промпта зарегистрировался, и не
доказывает, что языковой пакет несёт переводы. Две недорогие проверки закрывают
этот пробел:

- роут отвечает, когда host-половина жива: `GET /api/system-prompt.mod` — полный
  контракт в [README пакета](../packages/system-prompt-mod/README.ru.md#http-контракт);
- открой сессию и нажми **«Промпт»** — окно покажет текущий промпт. Его длина
  зависит от промпта развёртывания и слоёв пресета, поэтому не сравнивай её с
  числом с другой машины: важно, что промпт вообще появился. Строка с ошибкой
  означает, что роут ответил, но сборка промпта не удалась, — это другая
  проблема.

То же вручную: открой GUI и убедись, что

- в шапке сессии появился контрол **«Промпт»** (мод добавляет его в строку
  utilities шапки), и
- в **Настройки → Общие → Язык** предлагается **Русский**.

## Шаг 5 — отчитаться

Сообщи пользователю ровно следующее:

- какие пакеты установлены и куда,
- какие строки и в какой патч-файл добавлены,
- что страницу нужно обновить,
- как откатить: `node tools/install.mjs --uninstall`.

## Разбор проблем

| Симптом | Причина | Что делать |
|---|---|---|
| команда `dsh` вообще не найдена | DSH ставился через npx и не был слинкован в `PATH` | найти запускатор и вызвать его через node: `Get-ChildItem "$env:LOCALAPPDATA\npm-cache\_npx" -Recurse -Filter bin.js \| Where-Object FullName -like '*@deepseek-ai\dsh*'`, затем `node <этот файл> web` |
| `dsh` падает с `…dsh.ps1 cannot be loaded because running scripts is disabled on this system` | политика выполнения PowerShell блокирует обёртку в Windows | **Не меняй политику безопасности машины по своей воле.** Вызови запускатор напрямую: `Get-ChildItem "$env:LOCALAPPDATA\npm-cache\_npx" -Recurse -Filter bin.js \| Where-Object FullName -like '*@deepseek-ai\dsh*'`, затем `node <этот файл> web --no-open --port <свободный порт>`. Ослабление политики (`Set-ExecutionPolicy …`) — общесистемное изменение, которое *пользователь* может выбрать сам, но это не шаг этого регламента |
| `boot-check` пишет `cannot read the browser-session secret` | каталог ещё ни разу не загружался, поэтому в нём нет `.credentials.yaml` | один раз запустить `dsh web` с этим каталогом и повторить пробник |
| `boot-check` пишет `cannot reach …` | `dsh web` не запущен или другой порт | запустить его или передать верный URL |
| `boot-check` пишет `the derived cookie was refused` | не тот домашний каталог (секрет принадлежит другой установке) | выставить `DSH_HOME` в каталог работающего сервера |
| Строки в патче есть, а мода нет в ростере | страницу не обновили, либо строка называет пакет, который загрузчик не может разрешить, — а строка, чей импорт однажды упал, остаётся упавшей | обновить страницу, затем посмотреть консоль браузера. Если мод всё ещё нет, проверьте, что пакет лежит в `@local/` под **своим именем** (`@local/dsh-locale-ru` → `dsh-locale-ru`), и перезапустите `dsh web` |
| Мод в ростере, но интерфейса нет | нужного слота нет в этой версии DSH | см. [Совместимость](../README.ru.md#совместимость); имя слота зависит от версии |
| «Русского» нет в списке языков | страница загружена до установки пакета | обновить страницу |
| Мод работал, потом правка файлов «откатилась» | в процессе остался старый модуль из кэша | перезапустить `dsh web` |
| После `dsh plugin --profile web …` моды исчезли | pnpm удалил пакеты, которых нет в манифесте профиля | снова `node tools/install.mjs` |

## Откат

```bash
node tools/install.mjs --uninstall
```

Удаляет пакеты, убирает ровно те строки, которые добавляет этот установщик, и
возвращает патч-файл к штатному пустому виду. После этого обнови страницу.

## Что здесь называется «установлено»

Это стоит знать, когда пользователь спросит, что будет при обновлении DSH:

- Моды — это плагины профиля: пакеты в
  `$DSH_HOME/profiles/node_modules/@local/` плюс строки в
  `cordis.patch.yml` профиля.
- `$DSH_HOME` **не является частью установки** DSH. Обновление или переустановка
  заменяет установку и не трогает домашний каталог — сессии, настройки, профили
  и эти моды остаются.
- Единственная операция, которая может их снести, — установка зависимостей
  профиля (`dsh plugin --profile <имя> …`), потому что она запускает pnpm.
  Повторный `node tools/install.mjs` всё восстановит.
